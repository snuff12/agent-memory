# 실사용 중심 에이전트 메모리 검토

[English](practical-memory-review.md)

검토일: 2026-10-14. **실제 작업에 도움이 되는 변경만 채택합니다.**
벤치마크는 조사할 단서이며 최적화 목표가 아닙니다. 아래 비교군은 공식 문서와 코드를
검토했습니다. 같은 환경에서 경쟁 시스템을 직접 실행해 순위를 매긴 결과는 아닙니다.

## 먼저 바로잡은 문제

이전 출력은 같은 문서의 두 번째 청크를 무조건 숨겼습니다. 여러 파일을 보여주는 데는
유리했지만, 판단에 필요한 같은 문서의 다른 근거를 놓칠 수 있었습니다.
배포 정책 예시에서는 배포 절차만 보이고 롤백 조건은 숨겨졌습니다.
출력 공간이 3,000바이트 이상 남아 있어도 그랬습니다.

실제 공개 코드인 `search.py`를 검토할 때도 재현했습니다.
`short_terms _format_bounded_search` 검색에서 관련 구간 두 개를 찾았지만,
제한된 출력에는 하나만 보였습니다. 문서 ID를 찾았는지만 세는 점수로는
이런 코드 검토 문제를 발견하기 어렵습니다.

현재는 서로 다른 문서의 첫 후보를 먼저 확보한 뒤, 여유가 있으면 같은 문서의
추가 구간도 담습니다. 출력 순서는 원래 검색 순위를 따릅니다.
배포 절차와 롤백 조건이 함께 보이는지 확인하는 회귀 테스트를 추가했습니다.

[기존 벤치마크 점수](../benchmarks/IMPROVEMENTS.ko.md)는 이 보완 전의
엔진 커밋 `ea53b90`에 대한 기록입니다. 이번 보완의 새 점수라고 주장하지 않습니다.

## 비교군에서 참고할 부분

| 비교군 | 확인한 방식 | 우리에게 필요한 검토 |
|---|---|---|
| [qmd](https://github.com/tobi/qmd) | 단어·벡터 검색, 질문 확장, 모델 재정렬, 검색 의도, `--explain` 진단 | 우리 기본 검색은 어휘 일치 중심입니다. 의미 검색은 별도 실험 기능이며, 일반 검색에 결합되지 않습니다. 표현이 다른 질문과 검색 실패의 설명을 개선할 여지가 있습니다. |
| [HippoRAG 2](https://arxiv.org/abs/2502.14802) | 문서·개체의 연결과 그래프 탐색을 통한 연관 검색 | 사람→프로젝트→설정처럼 여러 자료를 연결해야 하는 질문입니다. 전체 그래프 도입보다, 후속 검색으로 실제 문제를 푸는지부터 확인합니다. |
| [Letta의 파일 탐색 평가](https://www.letta.com/blog/benchmarking-ai-agent-memory/) | 에이전트가 질문을 바꾸고 검색·열기를 반복 | 우리도 도구와 계약상 후속 검색·읽기가 가능합니다. 다만 기존 평가는 원래 질문 한 번의 검색만 측정했습니다. 실제 에이전트의 작업 흐름은 별도 확인이 필요합니다. |
| [Graphiti](https://github.com/getzep/graphiti) | 사실의 유효 기간, 변경 이력, 원본 사건과의 연결 | 현재 기억 카드의 유효성·검토기한·대체 상태는 있습니다. 이것은 사건 시점 추론이나 ‘그때 유효했던 결정’ 조회 기능과 다릅니다. |
| [Mem0](https://docs.mem0.ai/core-concepts/how-it-works) | 사실 추출, 중복 제거, 임베딩, 명시적인 기억 수정 API | 우리 기억·종합 카드는 수동으로 정리합니다. 사용자가 허용한 저장에 한해 초안·중복·충돌 검토를 돕는 기능을 고려할 수 있습니다. 자동 대화 저장이나 자동 승격은 채택하지 않습니다. |

Mem0의 현재 문서는 관리형 Platform과 OSS 검색을 구분하고, 자동 추출은 추가 방식이며
기억 수정·삭제에는 명시적인 작업을 쓰도록 설명합니다. Graphiti와 관리형 Zep도
구분해야 합니다. 이들의 기능이나 발표 점수를 섞어 비교하지 않습니다.
특정 방식이 다른 시스템에 있다는 사실만으로 우리에게 효과가 있다고 판단하지 않습니다.

## 직접 확인한 부족한 부분

자동 확인에는 임시 합성 자료를 사용했습니다. 위의 공개 코드 검토는 별도의 읽기 전용
분석이며, 운영 중인 대화·기억·실패 기록을 공개 자료에 넣지 않았습니다.

- **긴 질문의 핵심이 잘릴 수 있습니다.** 검색어는 앞의 서로 다른 단어 12개만
  유지하던 상태였습니다. 합성 질문에서 마지막의 결정적 식별자가 빠지면 배경 문서만 나왔고,
  식별자만 검색하면 필요한 문서를 찾았습니다. 단순히 단어 수를 늘리기보다 파일명·ID·
  명시한 구절을 보존하는 방향을 실제 프로젝트 질문으로 검증해야 합니다.
- **표현이 달라지면 놓칠 수 있습니다.** `car repair`는 `automobile maintenance`
  문서를 찾지 못했고, 원문 표현으로 검색하면 찾았습니다. 어휘 검색의 한계를 보여주는
  예시이며, 특정 임베딩 모델이 해결한다고 검증한 결과는 아닙니다.
- **자료 사이 연결에는 후속 행동이 필요합니다.** `Mina database`는 Mina가 Aurora를
  담당한다는 기록만 찾았습니다. Aurora를 다시 검색해야 CockroachDB 설정이 보였습니다.
  반복 검색으로 해결할 수 있으므로, 그래프 DB 도입을 당연한 답으로 두지 않습니다.
- **문서를 찾아도 정답 구간을 읽지 못할 수 있습니다.** 찾은 프로토콜 문서의 뒤쪽
  보존 기간 값이 첫 1,200바이트 읽기에는 없었습니다. 더 크게 읽으면 나왔고,
  다음 읽기 안내도 정상적으로 표시됐습니다. 모든 읽기 예산을 늘리는 대신 필요한
  구간으로 이동하거나 후속 읽기를 하는 흐름을 확인해야 합니다.

기존 검색 실험에서 근거를 모두 찾지 못한 85문항은 여러 대화 종합 35개, 시간 추론
38개, 선호 5개, 어시스턴트 정보 5개, 정보 갱신 2개였습니다. 79문항은 BM25도
함께 놓쳤습니다. 이는 조사할 질문을 고르는 단서입니다. 원인이나 실사용 우선순위를
이 숫자만으로 확정하지 않습니다. 긴 대화 평가를 코드·연구·프로젝트 기억 전체의
성능으로 일반화하지 않습니다.

## 검토 후 반영한 변경

긴 질문의 파일명·ID·코드 심볼·인용한 단어를 기존 12개 제한 안에서 우선 보존하고,
나머지 자리에 앞뒤 문맥을 담도록 바꿨습니다. 명시한 단어를 본문에서 찾는 별도 경로로
일반 문장보다 정의·호출부를 우선하고, 파일명을 함께 적은 질문도 처리합니다.
`search --explain`은 검색어 선택과
허용된 검색 경로의 후보 수를 보여주며 피드백을 저장하거나 제외된 기억을 검사하지
않습니다. `read --query`는 같은 읽기 예산으로 원문 표현에 맞는 구간을 고르고
청크 문자 위치·생략 여부를 표시합니다. 검색·읽기에 기존 기억의 유효 시작일과
재검토일도 표시합니다. 특정 날짜의 사실 추론이나 자동 충돌 해결 기능은 아닙니다.

[사용 흐름](retrieval-workflows.ko.md)과 새 회귀 검증 10개에 이 변경, 범위를 유지한
후속 검색, 이전·현재 기억의 수동 비교를 담았습니다. 실제 공개 `search.py` 검토에서는
함수 정의와 호출부를 각각 1,200바이트로 읽어야 통과하며, 파일만 찾는 것으로는
충분하지 않습니다. 모델·그래프·자동 저장·승격은
추가하지 않았습니다. 벤치마크 데이터나 점수로 규칙을 정하거나 변경을 채택하지
않았습니다.

## 채택 기준과 남은 과제

| 순서 | 후보 | 실제 사용에서 확인할 것 |
|---|---|---|
| 반영 후 실제 작업 확인 계속 | 핵심 검색어 보존과 검색 실패 설명 | 긴 질문의 파일명·ID를 유지하고, 검색어 선택·원본 변경·적용 정책을 대화 기록 저장 없이 확인하는가. 제외된 기억의 존재는 진단하지 않음 |
| 반영 후 실제 작업 확인 계속 | 검색에서 필요한 원문 구간까지 연결 | 코드의 정의·호출부, 정책의 원칙·예외, 배포·롤백 조건을 필요한 만큼의 검색·읽기로 함께 확인하는가 |
| 범위를 유지한 흐름 확인, 사건 시점 추론은 별도 | 후속 검색과 시간·버전 구분 | 여러 파일의 결정을 연결하고, 이전 규칙과 현재 규칙을 원문 근거와 함께 구분하는가 |
| 조건부 | 선택형 의미 검색·재정렬 | 실제 표현이 다른 질문의 근거 확인에 도움이 되며, 지연·메모리 사용·범위 격리가 적절한가 |
| 조건부 | 기억 초안과 중복·충돌 검토 | 사용자가 허용한 저장의 검토를 쉽게 하면서, 원본·이력을 조용히 바꾸거나 inbox를 자동 승격하지 않는가 |

읽기 전용 원본, 원본 버전에 묶인 ref, 검색·읽기 양쪽의 검토·범위 검사, 명시적인 저장,
제한된 문맥이라는 장점은 유지합니다. 필요한 근거가 실제 전달됐는지, 작업 판단이
맞는지, 도구 호출·읽은 바이트·지연이 적절한지, 잘못된 버전이나 범위의 기억을
사용하지 않았는지로 판단합니다. 벤치마크에 기대 문서 ID가 더 많이 나왔다는 이유만으로
변경을 채택하지 않습니다.
