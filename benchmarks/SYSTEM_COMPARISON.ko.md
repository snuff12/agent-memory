# 외부 메모리 시스템 실제 비교

비교일: 2026-10-15. **원문을 정확한 위치에서 읽는 도구를 먼저 개선하고,
의미검색은 선택 기능으로 보완하는 방향**을 권합니다. 그래프·자동 사실 추출·재정렬을
기본 검색에 한꺼번에 넣을 근거는 확보하지 못했습니다.

qmd, HippoRAG 2, Graphiti, Mem0 OSS, Letta Code와 Sourcegraph SCIP Python
인덱서를 실제로 설치해 실행했습니다. 흉내 낸 자체 구현으로 대체하지 않았습니다.
SCIP는 코드의 정의·참조 위치를 찾는 비교군입니다. LLM은 요청대로 **구독 Codex**를
사용했습니다. 운영 기억과 인덱스는 변경하지 않았습니다.

일반 사실 추출과 에이전트 판단은 구독 Codex로 실행했습니다. qmd는 실제 기본 구성을
비교하기 위해 자체 로컬 GGUF 질의 확장·재정렬 모델을 유지했습니다.

Graphiti는 FalkorDB의 단독 `_` 검색어가 구문 오류를 일으켜, 문장부호만 있는
검색어를 제거하는 호환 수정을 적용했습니다. 단어와 원래 검색·그래프 흐름은 유지했습니다.
추출 사실 389개로 구문 오류가 사라졌는지 먼저 확인했습니다. 실패 상태는 보존했고,
빈 그래프와 기존 추론 캐시로 재실행했습니다. 수정 없는 원본 실행과는 구분합니다.

## 측정 조건

합성 자료와 공개 코드 93개 문서에서 질문 50개를 고정했습니다. 이전 질문 42개와
새 공개 코드 질문 8개입니다. 근거가 있는 질문은 46개이며, 4개는 자료에 답이 없습니다.
질문과 정답 근거를 색인이나 사실 추출 프롬프트에 넣지 않았습니다.
이전 질문도 추가된 문서들과 경쟁하므로, 앞선 42문항 실험의 백분율과 직접 비교하지 않습니다.

아래 숫자는 **미리 지정한 원문 근거를 전부 읽었는가**입니다. 답변 정확도나 실제 업무의
성공 확률이 아닙니다. 유용한 부분 설명도 엄격한 원문 검사에서는 실패할 수 있습니다.
반대로 근거를 다 읽었다고 설명까지 맞았다고 판단하지 않았습니다.
구체적으로는 반환된 원문에 미리 정한 문구가 들어 있는지 검사합니다.
함수 본문 전체나 정답 추론의 충분성을 자동 심사하는 검사는 아닙니다.

qmd의 벡터 검색은 현재 검색이 놓친 13개를 복구하고 코드 질문 1개를 잃었습니다.
전체 검색은 벡터 검색보다 원문 확보가 많지 않았습니다. 의미검색의 가치는 보이지만,
질의 확장과 재정렬까지 모두 도입할 근거는 약합니다. 모델과 입력 분할도 달라서,
차이를 알고리즘 하나의 효과로 단정할 수 없습니다.

## 검색어 변경과 후속 검색

같은 Codex JSON 컨트롤러와 원문 읽기 도구로 24개 질문을 실행했습니다.
컨트롤러는 Codex가 검색·읽기·종료를 선택하도록 한 간이 실행기입니다.
근거가 있는 질문은 20개입니다. 검색 최대 6회, 판단 8회, 원문 읽기 3회입니다.

| qmd 전체 검색 | 11 | 2 | 0 | 1 |

선택된 세 단계 연결 문제 2개는 현재 검색에서도 원문에 나온 이름을 따라 재검색하면
해결됐습니다. 모든 연결 문제에 그래프가 필요 없다는 증명은 아닙니다.
Mem0는 새 공개 코드 문제 3개를 추가로 복구했지만, 현재 검색이 풀던 1개를 잃었습니다.
추출한 사실을 정답으로 인정하지 않고 원문까지 읽어 검사했습니다.

## 실제 에이전트 도구

간이 컨트롤러와 실제 에이전트가 같다고 볼 수 없어 별도로 실행했습니다.

| 실제 실행 방식 | 필요한 원문 확보 /20 | 기존 공개 코드 /2 | 조건 |
|---|---:|---:|---|
| Codex + 현재 메모리 MCP | 11 | 0 | 같은 검색·원문 출력 한도 |
| Letta Code + Read/Grep/Glob | 20 | 2 | 최초 실험, 바이트 한도 다름 |
| Letta Code + 출력 한도 적용 | 18 | 2 | 같은 검색·원문 출력 한도 |

최초 Letta 실험의 출력은 한 문제에서 최대 13,139바이트였습니다. 이를 그대로 비교하지
않고 출력 한도를 맞춰 다시 확인했습니다. 한도를 맞춘 실험은 표현 문제 1개와 공개
코드의 범위 문제 1개를 놓쳤습니다. 셸·쓰기·기억 저장·하위 에이전트 도구는 껐습니다.

한도를 맞춰도 인터페이스는 다릅니다. Letta의 실시간 grep은 파일과 줄 번호를 확인한
원문을 반환합니다. 현재 메모리의 색인 스니펫은 별도 원문 읽기가 필요합니다.
프롬프트와 도구 설명도 다릅니다. 18 대 11을 검색 알고리즘만의 차이로 해석하면 안 됩니다.

실제 Codex 실행에서는 작은 `max_tokens` 요청 때문에 출처 정보를 넣고 나면 코드가
거의 남지 않는 사례가 나왔습니다. MCP 속성에는 이것이 토큰 수가 아니라 UTF-8 바이트
한도라는 설명이 빠져 있습니다. 같은 이름이 반복된 코드에서는 초점 읽기가 원하는 구현
대신 다른 위치를 보여주기도 했습니다. **원문 탐색 도구의 사용성**을 먼저 손볼 이유입니다.
